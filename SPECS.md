# Flashwright implementation specification

## S1 Purpose, authority and reading path

Flashwright is the project name; Playwright is the compatibility reference. Package names below are proposed release names, not a claim that those names are available or published

Build a Rust browser-testing engine and a first-class TypeScript library that can replace Playwright in existing TypeScript projects with minimal migration. Optimize action/assertion latency and suite throughput while preserving the compatibility contract in S4

Current state: the experimental TypeScript library launches the pinned Chromium through a persistent Rust driver, owns contexts/pages, evaluates values and navigates real HTTP pages with network and lifecycle events. Basic cookies and exact UTF-16 localStorage state now round-trip through objects/files and native runner fixtures; private origin pages preserve isolation, with the documented service-worker collection difference in S4.j. The isolated resident selector runtime now supports a tested slice of locator reads, waits, same-process child-frame queries, native text fill, selection, focus and native pointer actions with fresh frame stability, hit interception and navigation barriers. Undelayed pointer input now queues native events in order without reply barriers, and multiple pages retain the reference focus/visibility defaults. Native locator and page keyboard presses now cover the pinned key layout, platform editing shortcuts and cancellation cleanup. Retrying DOM assertions and an experimental native test-runner fixture/matcher adapter are available, with shared ESM/CommonJS runtime identities and packed consumer checks. Retrying ARIA snapshot matching and named file baseline updates now pass focused Bun and Node checks. Inline baseline proposals work under Node; Bun inline generation/update returns a typed unsupported error because the pinned reference runner cannot produce a usable patch there. The three preserved TodoMVC migration tests pass through packed packages with import/config changes only. Public default Page/Locator ARIA snapshots pass shared browser, trace-viewer and packed consumer gates; all 24 preserved offline TodoMVC tests pass on Bun and both Node versions. Default failure documents retain original attempt diagnostics and trace attachment bytes, with the combined implementation passing the full macOS core gate. Browser/process failure tests and shared navigation/locator/pointer/keyboard/assertion differential fixtures are available. Resident assertions pass host cancellation and lifecycle checks and are selected as the default supported assertion path after current conformance, complete-flow and resource comparisons; the separate 10% complete-flow release target remains unproven. Page screenshots now return PNG/JPEG buffers and atomic files with tested geometry, font/animation preparation and cleanup. JSHandle and ElementHandle base lifecycle, nested handle arguments, supported graph values and same-process frame evaluation now preserve original-context ownership with bounded allocation cleanup. Captured text selection and native scrolling now preserve that ownership; other element-specific operations and additional value classes remain unsupported. Live page/context console messages now retain original-context argument handles with exact diagnostics and bounded background cleanup. Console history, workers and out-of-process frame delivery remain unfinished. Common local Download methods and normal-context/runner policy now pass pinned differential, stream-lifecycle, guardian, packed-consumer and trace checks. The preserved SVGOMG migration passes five of six tests; its remaining out-of-process frame evaluation is unsupported. Native Linux measurements remain unverified. The complete runner adapter, broader navigation/frame/value conformance, remaining artifacts and release performance gates remain unfinished. For verified progress and remaining gates, read [compatibility/milestones.json](compatibility/milestones.json); reference identities and retained evidence are in [compatibility/reference-manifest.json](compatibility/reference-manifest.json). The exploratory prototypes and their raw measurements have been removed; requirements below remain delivery contracts rather than claims of shipped coverage

a. For implementation planning, read S2–S6, select the first incomplete milestone in S5, then load the sections named in that milestone
b. For TypeScript migration or runner integration, load S7–S9 and S18
c. For engine operations, load S10 and the applicable semantic section S11–S14
d. For optimization, load S6 plus S12, S16 or S17 as applicable; a faster result doesn't override S4
e. For publication, apply S18 and the release gates in S19
f. If a proposed change alters this contract, record the decision and update the affected section before implementation. This file is the source of truth for main-build requirements; it has no dependency on retired research files

Chromium on Linux and macOS is the initial delivery scope. “Any TypeScript project” is the migration ambition, not a claim that a Chromium-only first release covers Firefox, WebKit, every plugin or every private Playwright API

The delivery target is a practical drop-in replacement for most projects, not exhaustive Playwright parity. Prioritize frequently used browser, assertion, fixture, authentication, networking and artifact features against a representative migration corpus. Keep the efficient independent implementation and explicitly classify uncommon gaps. A large declaration inventory is a coverage map, not a requirement to implement every entry before proving useful replacement coverage and complete-suite performance

The primary objective is decisive, reproducible performance leadership while approaching drop-in use across almost any Playwright codebase in the declared browser scope. Small unresolved gains do not meet that ambition. Modified Chromium, native browser operations, renderer preparation and a different browser architecture are valid experiments when they preserve real application behavior and improve complete work. The current component choices are hypotheses, not limits on the design space; apply S6 evidence and S13 semantic gates to replacements

## S2 Selected decisions and rationale

Earlier exploration informed these choices, but its removed artifacts aren't reproducible evidence for the main build. Establish new baselines in M0 using S6; don't quote retired pilot numbers as verified product performance

| Decision | Reason | Implementation and validation |
| --- | --- | --- |
| Keep CDP as the initial coarse browser channel | Transport is one part of a pipeline that also includes readiness, input, rendering and application waiting | S10 and S13; attribute costs before replacing transport |
| Execute supported conditions beside the DOM | Subscriptions can reduce repeated coordination and delay after a condition changes | S12; retain full predicates, fallback detection and independent host deadlines |
| Offer explicit submitted sequences | Rust-owned loops reduce adapter traffic; renderer-owned loops can additionally reduce browser coordination | S16; compare both against ordinary calls, including preparation and real application work |
| Harden existing binary CDP for payloads | Chromium already has a binary pipe; Unicode conversion and base64 artifacts can make encoding material | S10; prove value/framing coverage and measure both small commands and large payloads |
| Preserve ordinary scheduling and fresh stability | Frame uncapping changes workload and scheduling; past geometry alone can't account for already-queued movement | S13; use fresh observation and current targeting by default |
| Separate controlled time from compatibility mode | Accelerating logical time can change frames, CSS animations and races with external clocks | S16; require explicit activation and a declared coverage contract |
| Make custom Chromium conditional | A coarse native operation may remove orchestration, but adds browser-build and maintenance cost | S13; require a compiled equivalent action and complete-flow evidence |

Application waiting bounds ordinary real-time execution. Removing coordination overhead helps only the portion of the critical path it occupies. Browser residency alone isn't a novelty claim, and neither a new encoding nor a Rust rewrite proves faster complete suites

## S3 Components and ownership

The default execution path is TypeScript facade → persistent Rust driver → Chromium, with a resident runtime in each participating document. Python and Playwright's browser driver aren't in this browser-command path

| Component | Owns | Doesn't own |
| --- | --- | --- |
| flashwright TypeScript package | Public browser objects, argument validation, callbacks, Promise/event delivery, engine startup and shutdown | Browser automation through a second Playwright backend |
| @flashwright/test package | Runner adapter, browser fixtures, Flashwright-aware assertions, config validation and artifact integration | A new scheduler in the first release |
| Rust engine | Browser/context/page/frame registry, semantic operations, deadlines, cancellation, protocol dispatch, cleanup and error records | Execution of arbitrary Node callbacks |
| Resident runtime | Lazy locator resolution, predicate checks, dependency subscriptions and bounded local execution | Final authority over host deadlines or process survival |
| Chromium backend | Real browser storage/rendering/network/input, document and target events | Reduced simulation of Chromium |
| External supervisor | Termination of stuck jobs and owned child-process cleanup | Replacing an explicitly unbounded public API timeout with an undisclosed timeout |

a. Run one persistent Rust driver per test worker by default, amortizing startup, and close it during worker teardown. Plain library calls start a driver lazily; closing the last owned browser releases its implicit driver and lets Node exit. An explicitly retained engine client has its own documented close/disposal contract
b. Use a Rust executable over bounded asynchronous IPC for the first TypeScript binding. A Node native addon is a later measured alternative, not an initial dependency
c. Use stock Chromium first. JSON pipe CDP is the complete baseline; select CBOR for a browser connection only after codec conformance and capability negotiation in S10. A connection has one negotiated encoding
d. Keep browser-engine operations behind a capability interface. An interface doesn't imply working Firefox/WebKit backends
e. Expose explicit extension APIs separately from Playwright-compatible methods. Ordinary calls don't silently compile or fuse user test code
f. Keep runner integration and engine independent: flashwright must work from a plain Node script, Vitest/Jest or another host without importing the test runner

## S4 Compatibility and unsupported behavior

The default target is documented Playwright behavior with faster condition detection. Initial compatibility reference: Playwright 1.60.0. Publish a tested version range only after S19; current online docs can contain newer APIs and don't silently expand that range

Decision order for every operation:

1. Validate its capability, arguments, ownership and options using S9. If unsupported, fail before starting that operation's browser effects
2. Apply the public method's contract, including its locator, timeout, event and completion rules
3. Choose a proven optimized implementation that satisfies that contract
4. If the optimized implementation doesn't cover the case, use a declared compatible implementation in the same engine
5. If neither implementation covers it, return UnsupportedFeatureError. Don't fall back silently to Playwright, synthetic input, a mock backend or another browser

a. Preserve supported return values, Promise rejection behavior, object identity, event ordering, strictness, matching rules, host callbacks, isolation, action completion and useful diagnostics
b. Faster checks may observe brief valid states that slower sampling misses. Record this difference in conformance cases; don't promise identical sampling traces or detection of every transient state
c. Preserve per-call timeout defaults and overrides. A segment budget isn't a replacement for ordinary per-step timeouts; apply S10 and S16
d. Unknown browser/method options aren't ignored. Custom runner fixture options are forwarded according to S8; they aren't mistaken for browser options
e. Unsupported means a specific typed capability failure, not a generic TypeError or a fabricated empty result. Include the method/option, value class, browser, reference version and documented alternative where one exists
f. Preserve user-requested semantics such as force, trial, dispatchEvent or clock control only when implemented. Their explicitly changed behavior isn't an ordinary-mode architecture speedup
g. Exact internal retry cadence, private channel objects, internal class brands and identical error-message whitespace aren't compatibility promises. Public error classes, meaningful messages, call sites and reporter integration remain required
h. Browser binaries, supported platforms and artifact capabilities are part of compatibility. Refuse an unavailable engine/platform or artifact policy explicitly
i. Browser-profile checks happen at configuration/launch time where possible. A Firefox/WebKit project or device configuration doesn't silently become Chromium
j. Basic storage snapshots collect existing cookie/localStorage state without executing application code in internal pages. Temporary origin pages bypass service-worker fetch interception. A pinned 1.60.0 differential found that its fallback page can execute a worker-supplied document and mutate the state being collected after all public pages close; Flashwright deliberately does not reproduce that side effect. Retain this behavioral difference in conformance evidence and release notes; it is not a performance equivalence claim
k. A screenshot that expires while queued must not prepare or capture the page later. The pinned 1.60.0 implementation can apply its temporary screenshot style after the active capture releases the queue, then reject without removing that style. Flashwright deliberately suppresses that expired work. Record this cleanup difference separately from shared image fidelity and do not count skipped expired work as a speedup
l. Primitive BigInt handles preserve their actual JavaScript value. The pinned 1.60.0 Chromium handle path converts BigInt to undefined, despite preserving it in ordinary evaluation. Flashwright deliberately avoids that data loss. This also applies to console argument handles and their value-derived message text. Retain a separate reference-difference case for handle creation, jsonValue and argument passing; don't report it as equal-result conformance or a speedup

m. File assignment rejects a target INPUT whose type is not file before mutating it. The pinned 1.60.0 buffer/clear path silently succeeds without changing a text input, while its local-path path retries until timeout. Flashwright deliberately reports that invalid target explicitly. Preserve this reference difference separately from successful-upload parity and performance comparisons.

n. Removing the last file-chooser listener cancels native adoption that remains unpublished when the removal is accepted. A later subscription does not reactivate that cancelled work. The pinned1.60.0 implementation can finish old adoption and deliver it to a newly registered listener; a three-sample blocked-renderer reference probe confirms that race. Record this cancellation difference separately from shared chooser identity, assignment and event conformance. Events already published before removal keep ordinary event-queue semantics.

o. A Download stream retains its original context ownership. Context closure or successful artifact deletion destroys active streams with an observable TargetClosedError, including consumption started after teardown. The pinned 1.60.0 stream can instead produce an unhandled asynchronous `_read` rejection and leave consumption pending after context closure. Flashwright deliberately returns a stream error; retain this diagnostic difference separately from shared download-byte and lifecycle conformance, and never count the reference hang as a speedup.

For assertions, consult [published retry semantics](https://playwright.dev/docs/test-assertions) when resolving a sampling question. For action checks, consult [actionability](https://playwright.dev/docs/actionability) and then apply S13. For a timeout question, consult [timeout categories](https://playwright.dev/docs/test-timeouts) and apply S10

## S6 Benchmark rules and claim acceptance

Use these rules for every claimed improvement, including adapter overhead, transport, subscriptions, native endpoints, artifacts, startup and suite scheduling

a. Match well-configured Playwright TypeScript/JavaScript on the same Chromium binary, revision, flags, fixture, backend, context isolation, viewport, artifact policy and resource budget. Python is a secondary attribution comparator, never the only baseline for a TypeScript replacement
b. Record OS/architecture, CPU/memory, display/headless mode, exact packages/toolchains, browser flags, source and executable hashes, worker counts and configuration. Distinguish reference-browser comparison from a custom-browser cross-build comparison
c. Rotate execution order across independent launches, warm deliberately and retain every valid sample. Record failures and the declared exclusion policy; don't rerun only unfavorable timings
d. Separate no-op latency, warm action/assertion latency, detection lag, cold launch, context/application preparation, real application waiting and suite wall time. Report complete preparation-inclusive observations alongside warmed paths
e. Include interaction-heavy, assertion-heavy, navigation-heavy, setup-heavy, backend-heavy and failure-heavy workloads. M0 must contain an application with real network/backend work as well as deterministic microbenchmarks
f. Retain sample counts, distributions, medians and observed tails. With too few observations for a tail estimate, report observed maxima instead. M0 sets sampling policy, confidence method and material-regression thresholds before final comparisons; analyze independent-launch variation
g. Count operations/evaluations, trusted input, protocol and adapter crossings, payload bytes, discovery visits, artifact output and backend requests where relevant. Different legitimate schedules can change reevaluation counts; disclose them rather than forcing artificial equality
h. Measure CPU and memory with explicit process-tree coverage. Per-worker maximum RSS isn't summed concurrent browser memory; reconstructed protocol bytes aren't raw wire captures
i. Require applicable behavior and lifecycle gates before reporting an equivalent-operation speedup. A fast failing test, skipped predicate, dropped trace or missed callback isn't a win
j. Compare latency at matched concurrency and suite throughput at matched resource limits. Sweep contention; don't attribute additional hardware or workers to the engine
k. Keep controlled time, replay/mocking, selected-test execution, altered stability, skipped animations and reduced artifacts in separate result classes. Apply S4.f
l. Store implementation benchmark workloads and configurations under benchmarks/ with executable harnesses and verifiers. Preserve immutable result snapshots, raw data, hashes and run metadata under benchmarks/results/. Record source hashes and licenses for reused code
m. Publish a speed claim only with a metric, workload, baseline, machine, retained result file and limitations. “Fastest” requires a declared competitor set and reproducible results; an isolated benchmark doesn't prove superiority over every alternative
n. Deliver a complete benchmark comparison table covering the fastest relevant contenders and the most popular E2E alternatives in the declared competitor set. Record why each competitor was included, exact versions, matched workloads and resource budgets, startup and complete-suite time, action/assertion latency, CPU/memory, uncertainty and failures. Unsupported or noncomparable cases remain explicit; never substitute an unmeasured estimate for a result

M0 records numeric acceptance thresholds in versioned benchmark configuration, with rationale. Until then this spec defines an optimization objective, not an invented speed guarantee

The initial broader contender set is Playwright, Puppeteer, Cypress and WebdriverIO, alongside Flashwright. Pin their versions and selection rationale in `benchmarks/configurations/competitors.json`. Library-flow comparisons and actual test-runner suite comparisons are separate classes. First admit each adapter against real fixture outcomes, browser identity/launch flags, trusted input, backend requests, context isolation and cleanup; functional admission is not speed acceptance. Preserve native competitor APIs and document any assertion helper, polling choice, launch-policy override or input-event difference. Do not disable native action readiness to manufacture a faster comparator. A competitor that cannot execute equivalent work remains explicitly unmeasured or noncomparable for that case. Current Flashwright source/driver verification and S6 sampling/resource gates still precede a comparative performance claim.

Cypress's default runner is a separate outcome-admission class: keep ordinary test isolation, click/type commands and native failing tests. Record dispatched-event trust, per-test page/storage reset, proxy/runner launch policy and expected versus unexpected failures. A successful outcome admission does not pass the native-input/fresh-context functional gate or authorize a library-flow speed comparison. Do not suppress the runner's expected failures or silently replace its default input with a plugin. A future native-input plugin configuration needs its own pinned class and evidence.

c. Preserve documented names, overloads, generic inference and callback types for the reference API. Derive or copy public declaration shapes with upstream notices and provenance; engine implementation types stay separate
d. Keep synchronous locator construction and normal Promise-based operations. Preserve Page/Context/Browser object identity and event-listener behavior; don't return raw protocol objects

f. Use explicit imports as the preferred migration. Change imports in tests, fixtures, page objects and configuration, and change the test command. Test bodies and fixture logic remain intact within the supported surface
g. Offer zero-import migration through verified package-manager aliases or supported resolver integrations. A tsconfig paths mapping alone isn't runtime module replacement. S18 installation tests must exercise both runtime and declarations
h. Do not promise interoperability with unmodified plugins that inspect Playwright internals or require actual Playwright class identity. Preflight-known incompatibilities use S4.e; list tested public-API integrations
i. Inventory public package subpaths as well as object members. Alias-mode tests include playwright/test and @playwright/test/reporter. A playwright-core alias is claimed only after its own exported surface passes; private deep imports aren't covered

This follows a packed-consumer reproduction in which aliasing the implementation itself created separate Page/Locator classes. The optional `flashwright/test` entry point uses the optional `@flashwright/test` peer; alias configurations that use `playwright/test` also install this canonical peer. Ordinary library imports must remain independent of runner installation

Selected Yarn scope: library imports, declarations and native browser operations are tested with both node-modules and PnP. Runner execution uses node-modules. The pinned upstream runner's separate ESM loader fails under PnP archive loading; extracting that dependency also failed mixed-module test discovery. The CLI must reject PnP runner execution before loading configuration or tests, with guidance to select `nodeLinker: node-modules`. Retain both failed experiments; do not advertise PnP runner parity or mutate consumer module resolution

```ts
const browser = await chromium.launch();

```

## S8 Playwright Test runner integration

Reuse the pinned Playwright Test scheduler and fixture lifecycle through a dedicated versioned runner adapter. This avoids building retries, sharding and reporting before delivering the new browser engine. It is a product dependency with licensing and maintenance cost, not evidence of engine compatibility

The canonical runner owns a checksum-pinned copy of the 1.60.0 runtime under its packaged dist/upstream tree. Its worker bundle adds one synchronous original-attempt callback after capture-policy normalization and before live trace writes or fixture resolution; all other upstream files remain byte-identical. Fixture sentinels alone cannot cover a last skipped test that reaches final stop without running fixtures, or prevent early SerializedFS live writes. A handled callback prevents upstream allocation; a declined or absent callback keeps the original path. Do not accept asynchronous disposition that could resume live allocation after final stop. Preserve the package name/exports for upstream self-resolution, relative worker/loader paths, notices and exact playwright-core dependency. The CLI, test exports and private globals use the same owned tree through ordinary module resolution. Keep the original isolated dependency for declaration types/build input without loading its test runtime. [Owned runner provenance](compatibility/upstream/owned-runner-provenance.json) records the source tree and adaptations. This change retains the scheduler and does not enable public automatic tracing.

a. Isolate the upstream runtime under an internal dependency identity. Resolve it from our dependency tree, not the consumer's @playwright/test import, which may alias back to us. Verify no recursive imports, duplicate runner instances or accidental upstream browser launch in S18
b. Prefer documented fixture/expect extension points. Keep unavoidable private integrations inside the versioned adapter, with source provenance and tests; no private runner assumptions leak into engine contracts
c. Flashwright supplies browser, context, page and supported request fixtures, their teardown, and artifact hooks. Worker fixture configuration must key browser reuse correctly; each ordinary test/retry gets a fresh context
d. Generic value matchers may reuse the pinned assertion infrastructure. Browser/locator/Page matchers dispatch to Flashwright operations and retain negation, configured timeouts, soft failures and runner step reporting when claimed
e. Re-exporting upstream expect unchanged is insufficient: its browser matchers and fixture/artifact plumbing may require private methods. M0 proves the integration boundary; M2 completes the declared slice before release
f. Preserve test.extend generics, fixture dependency ordering/scopes, hooks, test.use, describe/parallel/serial behavior, retries, projects, worker identity, testInfo and attachments for claimed entries in S9
g. Forward supported runner configuration and custom fixture options to the runner. Validate native browser/context/engine options at their own boundary. Reject unsupported built-in project settings before starting tests where statically discoverable
h. Integrate runner timeout/cancellation with S10; a timed-out fixture or test can't leave resident subscriptions, routes or contexts alive. Teardown failures remain distinguishable from the original test failure
i. Keep runner reporters and attachments meaningful. Trace/video configuration is governed by S15; the adapter doesn't leave upstream artifact hooks operating on counterfeit Playwright objects
j. The CLI forwards supported test selection, projects, workers, retries, sharding, reporters and config loading to the runner adapter. Unknown flags fail with guidance; UI/codegen/debugger commands remain separate capabilities
k. Don't implement a replacement scheduler as a workaround for one private integration. If the versioned adapter can't meet a required public contract, isolate the root cause, record an architecture change and update S5/S8 before changing the delivery model

For fixture ownership questions, load [fixture extension and override documentation](https://playwright.dev/docs/test-fixtures). For integration changes, inspect the pinned [runner fixtures](https://github.com/microsoft/playwright/blob/v1.60.0/packages/playwright/src/index.ts) and [assertion wrapper](https://github.com/microsoft/playwright/blob/v1.60.0/packages/playwright/src/matchers/expect.ts). For config forwarding, load [configuration](https://playwright.dev/docs/test-configuration)

The library exports the pinned standalone device descriptor catalogue without a runner dependency. Known defaultBrowserType descriptor metadata does not change an explicitly selected Chromium browser; runner backend selection still rejects unavailable Firefox/WebKit. The experimental context device slice supports screen, userAgent, deviceScaleFactor, isMobile and hasTouch with native per-context emulation before document execution. Runner device presets inherit these values through contextOptions and honor explicit individual overrides, including false and scale one. The pinned runner ignores a top-level screen value; contextOptions.screen reaches the native context. Screenshot pixel scaling and limits include the configured device scale. Locale/timezone, touch action APIs, workers, popups and cross-process frame emulation remain outside this slice.

The experimental context-settings slice supports ignoreHTTPSErrors and javaScriptEnabled with their pinned defaults, false and true respectively. Validate before allocation and configure each public page before user init scripts or application navigation. Apply runner defaults to manual contexts and separately launched browsers, preserving explicit option overrides. Private storage pages retain their independent collection/restoration behavior. Verify HTTPS main documents/subresources and sibling isolation, disabled inline/external/event-handler execution, explicit evaluation, init-script behavior and navigation before claiming coverage. Accept explicit launch slowMo:0 as the ordinary no-delay mode; nonzero slow motion remains unsupported until its public-operation delay contract is implemented. The slice passes the 64-group Bun/native macOS development checkpoint plus focused headless-shell/full-Chrome differentials and packed consumers. This is development coverage; refreshed Node/package-manager/Linux matrices and release gates remain open

Public pages must explicitly apply the pinned media defaults before init scripts: color scheme light, reduced motion no-preference, forced colors none and contrast no-preference, with no media-type override. Inheriting operating-system preferences changes application CSS; a full-Chrome reference probe confirmed dark and higher-contrast inheritance while the headless shell happened to match. Verify initial pages, later pages, same-process child frames, navigation and computed styles on both browser builds. Explicit media overrides and Page.emulateMedia remain separate unsupported APIs; the default-policy correction passes the86-group native macOS Bun checkpoint and focused full-Chrome differential, including init scripts and computed styles.

Finish line: extended user fixtures, ordinary and soft assertions, test timeouts, retries, reporters and worker teardown pass against a packed adapter without upstream browser-driver execution. Private touchpoints and their tested reference version are recorded

Automatic trace integration uses an asynchronous versioned public-context observer. ## S10 Transport, operation state and process lifecycle

Use two separate protocols: TypeScript↔Rust application IPC and Rust↔Chromium CDP. Do not implement Playwright's private driver protocol as a prerequisite for TypeScript migration

a. Application IPC uses versioned length-prefixed messages, typed payloads and explicit binary/chunk attachments. Protocol 6 retains JSON control frames and request-scoped attachment streams: a start envelope declares encoding and encoded/decoded lengths, bounded data frames carry a zero marker, little-endian request identity and encoded offset, and a terminal result confirms complete delivery. Raw bytes and Chromium's existing base64 representation are distinct encodings; JSON CDP base64 can pass through without a redundant Rust decode/re-encode. A base64 stream uses complete four-character groups. Enforce exact offsets, lengths, ownership and terminal state; errors discard incomplete data. Default limits allow 32 MiB decoded per attachment and two active attachments in each direction, with backpressure and cancellation while streaming. Chunk payloads are at most 64 KiB and complete frames obey the negotiated byte limit. Interleave other replies/events between attachment frames. The JSON browser boundary admits declared binary reply shapes separately from ordinary 8 MiB replies/events and outgoing commands. Its hard incoming wire ceiling is six times the maximum decoded attachment size plus 64 KiB for the envelope, accounting for JSON control-character escapes; decoded payloads still obey the negotiated attachment cap. A complete oversized reply below that hard ceiling rejects only its call, with no replay. Oversized events or a hard wire-ceiling violation invalidate the connection explicitly. Discard late cancelled replies without building their result values, and release large receive buffers after each frame. Standard streams don't mix logs with protocol frames; diagnostics go to a separate stream

Host-to-driver binary input is an implementation contract for the upload slice: a command optionally declares inputByteLength, followed by raw request/offset chunks and an explicit inputEnd terminal carrying aborted status. The engine cannot execute that command before complete input validation. Enforce the same negotiated 32 MiB per-input and two active input reservations independently of output reservations, so a body-bearing request cannot deadlock while returning a binary response. One input reservation stays owned through execution and terminal completion. Cancellation promptly releases incomplete payload bytes, while bounded discard metadata validates already-queued late chunks until inputEnd; the number of unclosed input streams is also bounded by the negotiated pending-operation limit. Rejected headers still own their stream termination. A cancelled sender stops producing chunks and closes that input stream explicitly; unrelated controls, cancellation and requests remain interleavable. Do not put file bytes into control JSON or restart the operation deadline after transfer. Optional traceCall metadata carries only the original context and recording generation for artifact input-activity hooks; stale or missing metadata cannot activate a replacement chunk. These additions require framing, backpressure, cancellation and real upload tests before coverage is claimed.

The browser-bound routing body transport has two typed exceptions: Fetch.continueRequest postData and Fetch.fulfillRequest body. Each consumes one already validated input attachment, up to 32 MiB decoded, and streams canonical base64 through a single non-interleaved CDP message with at most 64 KiB encoded scratch. Metadata retains the ordinary 8 MiB bound. The queued/writing message shares the original raw bytes and input reservation; cancelling its caller cannot release those credits or leave a partial JSON frame. Queued withdrawal suppresses the whole message, and a started message finishes or fails the connection. Ordinary outgoing commands and reply/event admission keep their existing limits. This transport alone does not establish public routing coverage or enlarge original-request observation limits; occurrence metadata, redirects and public body delivery require their own end-to-end verification.

c. Command envelopes identify request, operation, context, page/frame, document generation, parameters and deadline policy. Terminal results include outcome, value/error, ownership metadata and bounded diagnostics

Validate and encode terminal replies before writing any bytes. An oversized result/error rejects that call without replaying effects, preserving input delivery and cleanup state. A canceled start retains cleanup ownership even when its response was not observed; late stop or activity from an older generation cannot affect a replacement. Initial page frames become exportable only after successful page publication. Exclude bulk screencast payloads from unrelated connection broadcast subscribers, including storage interception. Do not await CDP or create an unbounded task queue from synchronous event delivery

Each JPEG permits at most4MiB decoded bytes and its canonical base64 representation. Native retained frames permit128 entries and 16MiB encoded bytes per context, with32MiB encoded bytes across an engine; at most128 page capture owners may exist in an engine. Metadata claims retain queue ownership until an attachment slot is acquired; transferring a frame moves its buffer rather than copying it. Existing attachment slots cap transfers at the lesser of2 and the negotiated limit, so frame transfer payloads add at most two canonical base64 representations of4MiB images. Host frame collection permits at most two concurrent transfer-through-resource-ingest owners per engine, at most one per context, adding at most8MiB decoded bytes. Validate the exact reserved decoded byte length before attachment allocation, and validate encoded length before decoding. Hold that host slot through file ingestion, and admit no unbounded waiting list. Per-page native ACK queues permit32 entries plus one delayed ACK; host activity coalescing permits128 pending page identities

These stage caps give at most 32MiB queued encoded payloads plus two base64 representations of4MiB images plus8MiB host decoded payloads, approximately50.67MiB, before bounded framing scratch, metadata and ordinary transport/writer buffers. Account these additional buffers separately: one synchronous incoming event per participating browser connection within the unchanged8MiB ordinary CDP event cap, at most16MiB receive-buffer capacity while assembling an accepted event of at most8MiB, and8MiB retained raw event plus one canonical frame representation during admission, existing64KiB attachment chunks, and the existing4MiB chunk writer queue. The unchanged connection framing layer separately permits up to192MiB+64KiB of wire-buffer capacity per browser connection for fully escaped typed bodies or an oversized event before classification; the8MiB ordinary-event limit applies after assembly. These are conservative logical-buffer bounds with explicit per-connection/per-chunk multipliers, not an RSS limit. Resource storage and archive limits remain those of the source/resource contract. Overload makes export fail explicitly rather than returning a silently partial filmstrip

Stamp frame receipt with a native monotonic clock and map it into the host action clock using a bounded per-chunk request/response sample. Retain the sample and its uncertainty in the context-options flashwrightClock field, and retain the compositor's independent frameSwapWallTime; do not stamp frames at delayed host-pull arrival or infer a tolerance from same-process reference observations. Delayed-collection checks must preserve the native capture time within the recorded clock interval rather than importing a same-process tolerance. Archive each frame event only after its immutable resource and alias are owned. Seal admission, settle collection and retain late cleanup under the existing export deadline, atomic commit and recording quarantine rules. Off sends no screencast/activity commands and allocates no frame payload owners

The development verification covers macOS arm64 with pinned Chromium148 headless shell and full Chrome under Bun1.4.2, including actual viewer image hashes, tiny/odd/scaled viewport cases, new/closed pages, chunk gaps, unfinished calls, overload, blocked-browser cancellation and packed aliased ESM/CommonJS runner consumers. Node22.22 and24.15 additionally pass the host collector, attachment and native boundary cases on headless shell. Independent captures can include different early or closing-page surface sizes; preserve and decode every frame, and compare the final reference geometry rather than requiring identical sampled geometry sets. This evidence does not establish Linux/Windows support or a performance claim.

Finish line: artifact fidelity, file/buffer outputs, viewer expectations, reporter attachments and failure diagnostics pass the declared policy corpus; resource limits don't silently omit requested data

## S16 Explicit sequences and controlled time

Ordinary Playwright-style calls retain S4. These extensions have distinct contracts and release labels

a. Submitted sequences contain finite validated operation descriptors, not arbitrary JavaScript/Python code. Expose them through flashwright/experimental with capability/version metadata
b. Offer Rust-owned sequencing first where host/native integration is needed, and renderer-owned assertion segments for validated local phases. Choose placement explicitly or by a disclosed planner with identical declared semantics
c. Preflight a sequence's supported syntax/options before starting. Resolve targets and execution-time conditions at the correct step; don't fail future locator checks prematurely
d. Preserve order, fail-fast behavior, completed indices and the first failed step when recoverable. If a renderer is lost, report unknown internal progress rather than inventing an exact index
e. Define the shared monotonic budget and required task/microtask yields. It isn't a transparent transformation of per-step timeouts or arbitrary await interleavings
f. Host callbacks/services, unsupported native operations and document transitions form explicit boundaries. Initial renderer segments are assertion-only and document-bound; stop or split before a boundary
g. No implicit action speculation, skipped predicates or unsupported branches. Expired/cancelled plans start no additional operations; apply S10 delivery and cleanup rules
h. Benchmark both sequence owners against ordinary TypeScript calls on the same predicates, diagnostic policy and application work, including plan preparation. Apply S6; an immediate-assertion workload isn't a representative application suite

Unsupported combinations reject before activation

Maintain a real host deadline and declared synchronization with external work. Existing Playwright clock APIs are a required comparator when applicable. Never enable virtual time, frame uncapping or animation skipping from an ordinary config as a hidden speed optimization

Finish line: each extension passes its own order, yield, deadline, cancellation, callback and lifecycle corpus; controlled-time results retain separate coverage and benchmark labels
